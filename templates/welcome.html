Welcome to RPA UI Log Analyzer

This prototype applies RPA UI interaction patterns to help automation designers move beyond replaying recorded clicks and keystrokes. Upload a UI log (CSV) and it identifies the UI activities a bot has to perform, matches each to a pattern, and recommends a prioritised list of automation methods for its execution environment. The analysis runs step by step, following the seven steps of the pattern-guided automation method recommendation approach, and shows the sequence of UI activities as a directly-follows graph.

Stage 1: UI activity identification

Steps marked LLM send data from the log to a language model, which takes the place of a subject-matter expert; Rule-based steps apply fixed rules; Lookup steps make no model call. There is no fallback: if the model is unavailable or returns an invalid answer, the analysis stops with an error rather than producing degraded results.

1
Segment events by context Rule-based

When the log is loaded, an LLM identifies the role of each attribute by what it describes, not by its name: the application (software context), the further context such as webpage, window or worksheet (data context), the target element, and the attributes indicating each execution environment. The activity-name attribute is proposed by the LLM and confirmed or changed by you. Consecutive events then stay in one interaction segment as long as they share their software context; within it, a change of webpage, worksheet or UI element starts a new segment. A value that was not recorded is no evidence of a change.

2
Abstract higher-level UI activities LLM

In place of a subject-matter expert, an LLM decides which consecutive events share one intent and form one UI activity: one action on one target. Repetitions of an action and events that only record its effect (such as the change of a field when it loses focus) belong to that action; clicking a text field before pasting into it is a UI activity of its own. Segments may be divided and adjacent segments combined, but not across a changed application.

3
Normalise UI activities LLM

An LLM normalises each UI activity to the vocabulary of the 13 RPA UI interaction patterns, by the meaning of the interaction rather than the words of the log, and names it by action + object + context (e.g. Write First Name field on rpachallenge.com in Edge). It returns the pattern, whose action is the normalised action, or none — the UI activity is then reported as not covered by the collection.

4
Add implicit activities Rule-based

UI activities a bot must perform but the log does not record are inserted by three rules, in this order: Switch context, Find, Focus (see below).

Stage 2: Method recommendation

5
Match patterns Lookup

Each UI activity matches the pattern of its normalised action; implicit activities match the pattern they were inserted for. No model call is made.

6
Determine environment and object type Rule-based

The execution environment is the richest one indicated by the attributes recorded for the UI activity's events: web, then desktop, then screen. It determines the object type: HTML, UI or visual element. Switch Context always takes the desktop environment; if no environment attribute is recorded, the environment is unknown.

7
Recommend prioritised methods Rule-based

The applicable methods of the pattern are listed in priority order — content-level (DOM), then accessibility-level (UI Automation), then visual recognition and hardware simulation — at most three. On the results page you can select another method for each activity; the export uses your selection.

Implicit Activities (step 4)

Three rules insert activities that are not recorded but that a bot must perform, applied in this order to each UI activity. An element is therefore found, then focused, then written to.

Switch context Rule

When a UI activity is recorded in a different application from the last recorded one (e.g. Excel → Edge), a "Switch context from A to B" activity is inserted. A missing application value is no evidence, and a different webpage within the same application is not a switch. Switching always takes place on the desktop.

Find Rule

Every action on a target element requires the bot to locate it first: Read, Observe, Write, Delete, Disable, Activate, Hover and Focus, and Scroll and Refresh when they act on an element rather than a whole page. A Find is inserted unless the preceding activity targets the same element. Open, Switch Context and Find need no Find.

Focus Rule

Writing into an element, or deleting data within a text field, requires it to be focused for input: a Focus activity is inserted before a Write activity, or a Delete of data within a text field, unless the preceding activity focuses that element. Deleting an element itself, such as a window, needs no Focus.

RPA UI Interaction Pattern Library (13 patterns)

All UI activities are normalised to the 13 RPA UI Interaction Patterns below. Each pattern has a fixed Action and Object, one or more supported execution environments, and a category.

Extraction — read or locate data without modifying the UI
Find Element Read Element Observe
Modification — change or remove UI content
Write Element Delete Element Disable Element
Control — navigate, trigger, or manage UI state
Open Activate Hover Switch Context Scroll Focus Refresh

Method Computation by Execution Environment

The recommended automation method depends on both the matched pattern and the identified execution environment. The table below summarises the first method recommended in each environment; lower-level methods follow it in the prioritised list (e.g. web: DOM → UI Automation → visual recognition / hardware simulation).

Environment Detection signal Extraction method Modification / Control method
Web Attributes describing an HTML element or browser location (identified by the LLM) HTML DOM parsing HTML DOM manipulation
Desktop Attributes describing a native application interface or document (identified by the LLM) UI Automation (UIA) tree parsing UI Automation (UIA) manipulation
Screen Attributes holding screen coordinates (identified by the LLM) Visual recognition Hardware simulation

Note: Switch Context is Desktop-only. Hover on Web also supports hardware simulation as an alternative.
