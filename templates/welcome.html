Welcome to RPA UI Log Analyzer

This prototype applies RPA UI interaction patterns to help automation designers move beyond simple click/keystroke replay. Upload a UI event log (CSV) and the tool will infer human-intent activities, match them to recognised RPA patterns, and recommend the appropriate automation method for each — broken down by execution environment. The analysis runs as a guided, step-by-step workflow and visualises the activity sequence as a directly-follows graph.

Recommendation Pipeline

The pipeline implements a two-stage recommendation approach. In UI activity inference (steps 1–3), consecutive UI events are grouped by their collective intent and the UI activity that produced each group is inferred and named using the pattern vocabulary. In method recommendation (steps 4–6), the matched pattern and execution environment determine a prioritised list of automation methods: content-level (DOM) → accessibility-level (UI Automation) → visual/input-level (visual recognition, hardware simulation).

Steps marked LLM send data to a language model; steps marked Rule-based use deterministic logic; steps marked Lookup make no model call — they read what the LLM already decided in step 2. An LLM is required — the pipeline has no rule-based fallback, so if the model is unavailable the analysis surfaces an error rather than producing degraded results.

1
Event Grouping Rule-based LLM abstraction

Consecutive events are grouped into interaction segments based on their collective intent — events that together constitute a single coherent interaction belong in the same group. The LLM first reads the CSV header and sample rows to identify which columns carry context (for example the application, webpage, URL, or element — column names differ between loggers). A shared value in one of these columns serves as supporting evidence for grouping, and a change of the recorded application value closes the current group and starts a new one — a candidate application boundary (an event with no application value is not treated as a change). An LLM second pass then turns these candidate groups into UI activities — one action on one target each: it sees the numbered events with their target elements and may divide a group (clicking a text field focuses it; pasting into it writes) or combine events of adjacent groups (a paste and the value-changed event it causes form one Write). It is shown the application-related attributes (then URL, window and element values) on both sides of every boundary; a changed application counts strongly against combining.

2
Activity Naming LLM

Each interaction segment is sent to an LLM (batched in groups of 5, processed sequentially to respect rate limits). The LLM interprets the group's collective intent and assigns an activity name — verb + object aligned with the pattern vocabulary, made unique and context-specific by including the concrete detail that sets the interaction apart (e.g. 'Write "John" into First Name field' versus 'Write "Smith" into Last Name field'), so no two activities share a name. It also returns the best-matching RPA pattern name (or none, when no pattern fits — the activity is then reported as not covered by the collection), the concrete target element, supporting evidence observations, and a confidence score. Implicit activities are then inserted by fixed rules (below).

3
Action / Object Extraction Lookup

The Action and Object are taken directly from the RPA pattern the LLM assigned in the previous step — every pattern carries a canonical Action/Object pair in the AOMC (Action-Object-Method-Context) vocabulary (e.g. Activate / Element, Write / Element). Application-specific log verbs ("click / press / tap", "type / paste / fill", "getCell", …) were already resolved to that shared vocabulary by the LLM when it chose the pattern in step 2, so this step makes no model call and uses no hardcoded keyword map.

4
Pattern Matching Lookup

The activity is matched to a pattern in the RPA UI Interaction Pattern Library using the pattern name the LLM assigned in step 2, by a case-insensitive name match only. Whether the pattern can be carried out in the identified execution environment is checked in step 6, so an activity keeps its pattern even when that pattern has no variant for the environment. This step makes no model call and has no rule-based fallback: if the LLM did not supply a usable pattern, the recommendation is left without a pattern assignment rather than guessed from keywords.

5
Context Identification Rule-based LLM columns

When the log is loaded, the LLM reads the CSV header and sample rows and identifies which columns indicate each execution environment, by what the column describes rather than its name (column names differ between loggers). Each UI activity's environment is then decided in priority order:

1. Web — if any of its events recorded a value in a web column (properties of an HTML/DOM element or browser location, e.g. XPath, tag, URL).
2. Desktop — otherwise, if any event recorded a desktop column (native application UI or document structure, e.g. application, window title, workbook, cell).
3. Screen (visual) — otherwise, if any event recorded a screen column (raw coordinates).
4. Unknown — if none was recorded.

6
Method Recommendation Rule-based

The matched pattern carries a Method field listing its variants, separated by " / " (e.g. "HTML DOM manipulation (Web) / UI Automation manipulation (Desktop) / Hardware simulation (Visual)"). Applicability is cumulative: a web activity can use content-, accessibility- and visual/input-level methods, a desktop activity accessibility- and visual/input-level methods, and a screen activity visual/input-level methods only. The applicable variants form a prioritised list of at most three methods, content-level first. If the pattern defines no applicable variant for the identified environment (for example Delete Element on screen — an element cannot be deleted from an image), no method is recommended and the reason is shown instead.

Implicit Activities

Three types of activity are inserted into the sequence by fixed rules, applied in this order — they are not recorded in the log but are necessary for a realistic RPA bot design. An element is found, then focused, then written to.

Context Switch Rule

When an activity is recorded in a different application from the last recorded one (e.g. Excel → Edge), a "Switch context from A to B" step is inserted before it. A missing application value is no evidence, and navigating to another page within the same application is not a switch.

Find Element Rule

When an activity acts on a specific element (read, observe, write, delete, disable, activate, focus, hover), the bot must locate it first: a "Find [element]" step is inserted, unless the preceding activity already targets the same element. Page-level actions (open a URL, scroll, refresh) get no Find step.

Focus Rule

Writing into an element requires it to have input focus: a "Focus [element]" step is inserted before a Write activity unless the preceding activity focuses that element. It is essential when the bot uses hardware simulation.

RPA UI Interaction Pattern Library (13 patterns)

All activities are matched against the 13 RPA UI Interaction Patterns below. Each pattern has a fixed Action and Object, one or more supported execution environments, and a category.

Extraction — read or locate data without modifying the UI
Find Element Read Element Observe
Modification — change or remove UI content
Write Element Delete Element Disable Element
Control — navigate, trigger, or manage UI state
Open Activate Hover Switch Context Scroll Focus Refresh

Method Computation by Execution Environment

The recommended automation method depends on both the matched pattern and the identified execution environment. The table below summarises the top-priority method for each environment; lower-level methods follow it in the prioritised list (e.g. web: DOM → UI Automation → visual recognition / hardware simulation).

Environment Detection signal Extraction method Modification / Control method
Web Columns describing an HTML element or browser location (identified by the LLM) HTML DOM parsing HTML DOM manipulation
Desktop Columns describing a native application UI or document (identified by the LLM) UI Automation (UIA) tree parsing UI Automation (UIA) manipulation
Screen Columns holding raw screen coordinates (identified by the LLM) Visual recognition Hardware simulation

Note: Delete Element does not support the Screen environment. Switch Context is Desktop-only. Hover on Web also supports hardware simulation as an alternative.
